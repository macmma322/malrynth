# Hardware risk register

Qualitative likelihood/impact applies to a tiny independent-OS team, not the general PC ecosystem. Decision deadlines are milestone gates, not dates.

| Risk | Likelihood | Impact | Evidence | Mitigation | Fallback | Decision deadline |
|---|---|---|---|---|---|---|
| GPU port overwhelms kernel/platform work | high | critical | AMDGPU/i915 select large DRM memory/scheduler/display/firmware ecosystems; FreeBSD carries LinuxKPI | GOP through R0; one generation; design uAPI and reset tests first | simple framebuffer indefinitely; secondary Linux compute domain | before Phase C native modeset |
| NVIDIA interface/firmware/vendor dependency | high | high | open modules are Linux modules, Turing+ requires GSP, production userspace remains vendor stack | do not select NVIDIA for R0; monitor Nova/Nouveau/NVK and GSP terms | AMD first, Intel second | before any GPU procurement/port approval |
| Wi-Fi firmware/regulatory stack is underestimated | high | high | iwlwifi depends on firmware, mac80211/cfg80211, regulatory DB, supplicant/user policy | wired R0; choose replaceable PCIe adapter; define regulatory authority | isolated Linux Wi-Fi domain; USB Ethernet | before R3 adapter selection |
| Laptop ACPI/EC/vendor methods block basic usability | high | critical | ACPI embeds AML and EC; inventoried Acer adds battery/backlight/hybrid graphics/CNVi | desktop first; qualify one deliberately simple laptop later | boot-only secondary target, no certification | before R4 model selection |
| IOMMU firmware groups do not isolate desired device | medium/high | high | requester-ID scopes cannot compensate for missing ACS or multifunction coupling | dump DMAR/IVRS/topology before purchase; use add-in slots/controllers | keep driver in kernel; choose another board/slot | before user-space/domain isolation claim |
| IOMMU implementation corrupts memory | medium | critical | translation/invalidation/interrupt remapping are privileged, concurrent mechanisms | QEMU fault tests, deny-default maps, guard pages, staged single device | disable domain feature and run trusted kernel driver | before enabling real-device translation by default |
| Proprietary platform firmware/ME/PSP causes opaque failures | medium | high | both reference families depend on vendor UEFI and platform security/management firmware | exact firmware pinning, public recovery/update, table hashes, serial logs | second board family; stay on known-good firmware | before R0 exact-board qualification |
| Firmware update changes ACPI/topology or bricks board | medium | high | vendor updates can replace UEFI tables/microcode/settings | archive image/hash/settings, update only with recovery path and need | rollback/replacement board; retain last-qualified version | before changing qualified firmware |
| Microcode is stale or cannot be redistributed | medium | high | vendors recommend current firmware/early OS updates; format/licensing differ | begin with current vendor UEFI, record revision, research loader separately | qualify newer firmware/CPU family | before security/release claim beyond lab |
| NVMe device variation/firmware exposes recovery bugs | medium | high | retail family may change controllers; queues/reset/power states are complex | exact IDs/firmware, two vendors, conservative features, QEMU errors | known-good 970 EVO Plus/SN570; USB recovery media later | before persistent writable filesystem claim |
| Storage testing destroys founder data | medium | critical | owned 970 EVO Plus is active root disk | no destructive tests; backups; disposable partition/spare only; explicit harness guard | QEMU image/RAM disk | before first real write test |
| xHCI port is behind unexpected hub/controller | medium | medium/high | B550 example routes some rear ports through ASM1074 | board block diagram, port-by-port path record, direct root port first | PCIe xHCI test card later; alternate port/board | before R0 USB qualification |
| Malicious USB descriptors compromise kernel | high once broad devices allowed | high | descriptor-driven enumeration/HID/hubs are untrusted parsers | strict bounds, fuzzing, IOMMU, narrow allow-list during R0 | disable port/class, driver domain for hostile devices | before removing R0 USB allow-list |
| Counterfeit/misprogrammed I210/I350 adapter | medium | medium/high | marketplace adapter authenticity/NVM varies | reputable source, photos/markings, PCI subsystem/NVM checksum | industrial onboard I210 or verified used OEM card | before Ethernet adapter qualification |
| Realtek onboard NIC consumes schedule | high if selected first | medium | weaker public programming docs, many revisions/quirks | explicitly use discrete Intel NIC first | QEMU e1000/igb; USB Ethernet later | before first physical network driver |
| Serial header is not usable as 16550/RS-232 | medium | high for debugging | consumer manual may expose header without Super I/O identity/electrical detail | select documented industrial board, pinout/level check, loopback | PCIe 16550; POST LEDs/GOP | before declaring an exact R0-A board |
| GOP framebuffer disappears/corrupts after handoff | medium | high | GOP is firmware-initialized; cache/aperture behavior varies | record map, reserve aperture, test cache policies, serial authority | serial-only PHYSICAL-0; alternate display port/board | before PHYSICAL-0 pass |
| Power management causes hangs/data loss | high if enabled early | critical | deep CPU/device/suspend paths coordinate firmware and every driver | HLT/shutdown/reboot only; stage features; log transitions | disable deep states/ASPM/suspend | before each power feature graduates |
| Suspend/resume fails across GPU/USB/NVMe | high | high | state is whole-system and firmware/device-specific | defer; per-device callbacks, stress/fault testing | no suspend; clean shutdown | before later desktop suspend support |
| TPM becomes accidental boot dependency | medium | high | fTPM/PTT/discrete TPM state and ownership can change | discovery only; boot with TPM disabled/cleared; no sealed root key in R0 | software keys/manual unlock in research | before measured-boot/key-sealing prototype |
| Hardware availability/revision drift breaks repeatability | high | medium/high | retail SKUs disappear or change components | family requirements + exact database; qualify two boards/NVMe vendors; used market | R0-B family; QEMU models | before declaring `reference-supported` |
| Undocumented device or silicon revision blocks bring-up | medium/high | high | a familiar product name or class code does not establish a stable register interface, reset path, firmware contract, or compatible revision | require a public specification or independently reviewable permissive implementation before selection; freeze VID:DID, subsystem ID, revision and firmware in the hardware database | replace the controller/adapter or narrow support to the documented revision | before adding the device to any reference profile |
| Proprietary peripheral demands vendor daemon | high for gaming/laptop devices | medium | RGB, touchpad, camera ISP, audio DSP often need vendor policy/firmware | boring class devices, no RGB/wireless/KVM in R0 | replace external peripheral | at device shortlist review |
| Linux driver domain becomes permanent host dependency | medium | critical to independence | easiest short-term path can accumulate boot-critical services | prohibit root/console dependence; track native exit plan and TCB | remove unsupported device, stay native subset | at every domain milestone review |
| Domain/shared-memory compromise crosses isolation | medium | high | VFIO/virtio still expose host VMM and front-end parsers | least mappings, fuzz protocol, reset/revoke, minimal guest | native trusted driver or no support | before untrusted domain use |
| Vendor cooperation never materializes | high | high for closed classes | no promise of stable GSP, Wi-Fi firmware API, laptop details | design from public specs/code, select replaceable hardware | change vendor/device, narrow support | before reverse-engineering exceeds pivot gate |
| Anti-cheat rejects Malrynth or compatibility VMs | high | medium to product goals, low to R0 | anti-cheat trusts supported kernels/drivers/attestation and may forbid VMs | do not couple R0 hardware to gaming certification; seek vendor cooperation later | compatibility guest/dual boot; supported games only | before promising competitive-game support |
| Hardware video/compute distracts from display correctness | high | medium/high | VCN/HuC/CUDA/ROCm add firmware and separate user stacks | display/recovery/Vulkan first; separate support claims | software codecs/CPU compute | before GPU Phase E scope |

## Operating rule

Any critical risk without a tested mitigation blocks a support claim, not research. A workaround belongs in the database with exact scope; it does not become a hidden global default.

## Recommended integration

Founder review should assign owners and milestone gates if these risks enter project governance. This research intentionally does not edit existing risk, architecture, or roadmap files.
