# M0 — Boot and Diagnostics

**Status:** COMPLETE (2026-08-19)

## Objective

Prove that firmware can hand control to Malrynth Boot, which loads and enters a genuinely
separate Malrynth kernel on bare metal, and that the kernel can validate the handoff and
report diagnostics — with a deterministic, automated test.

## Dependencies

None. This is the first milestone.

## Scope (delivered)

- `malboot`, a UEFI application for `x86_64-unknown-uefi`.
- `malrynth-abi`, a versioned `#[repr(C)]` handoff contract with layout assertions under test.
- An ELF64 `PT_LOAD` loader that validates untrusted image input.
- Kernel placement at a fixed physical address, requested explicitly from firmware.
- Framebuffer discovery (GOP) and ACPI RSDP capture.
- `ExitBootServices`, and normalisation of the final UEFI memory map.
- `malrynth-kernel` for `x86_64-unknown-none`: `.bss` zeroing, handoff validation, 16550 UART
  diagnostics, and a controlled halt.
- A kernel panic backtrace: a frame-pointer walk in which **every frame is validated**
  before dereference, plus `tools/symbolize`, a host-side ELF symbol resolver. Symbolisation
  is deliberately outside the kernel: it would otherwise put a DWARF parser in ring 0.
- **Byte-reproducible builds**, enforced by `tools/check-reproducible`.
- `tools/`: `bootstrap`, `doctor`, `build`, `test`, `run-qemu`, `status`, `symbolize`,
  `check-panic-path`, `check-reproducible`, `scan-secrets`.
- A QEMU boot smoke test asserting an exact marker, with **verified failure detection**.

## Explicitly out of scope

Memory management, paging, heap, exceptions, interrupts, timers, SMP, user mode, processes,
threads, scheduling, syscalls, capabilities, IPC, ACPI parsing, PCIe, drivers, filesystems,
networking, graphics output, a GUI, compatibility, and every application. **No fake "OS"
window.** The framebuffer is discovered and deliberately not drawn to.

## Tests

`tools/test`: `fmt` → `clippy` (per target) → ABI layout unit tests → build → three
consecutive QEMU boots asserting the marker. Negative paths verified manually: absent kernel
image, and an ELF with corrupted magic — both produce `MALRYNTH_M0_BOOT_FAIL` and a non-zero
exit.

## Performance gates

Image sizes measured and recorded (`docs/performance/PERFORMANCE-CONSTITUTION.md`). Boot
timing is **not** instrumented: doing it honestly needs a calibrated timer, which is M1.

## Security gates

Untrusted input (the kernel image) is validated on the receiving side; the ELF parser
contains no `unsafe`; the kernel has zero external dependencies; every `unsafe` block carries
a `SAFETY:` justification. **Not** provided: image authenticity. An attacker who can write to
the ESP can replace the kernel — accepted and documented in `TRUST-BOUNDARIES.md`.

## Known limitations carried into M1

1. **Fixed load address.** The kernel is non-relocatable at `0x1000_0000` and depends on
   firmware honouring an exact allocation. M1 moves it to the higher half under
   Malrynth-owned page tables.
2. **`static mut` serial port.** Sound only while one execution context exists; must become a
   lock before SMP.
3. **No real ESP image.** `tools/run-qemu` uses QEMU's virtual FAT, so no distributable
   `.img` is produced. `mtools` is absent on this host and was deliberately not installed;
   `tools/doctor` reports it as optional.
4. **Boot-services memory not reclaimed.** Conservatively marked reserved; reclaiming it
   safely needs proof nothing retained a pointer.
5. **Boot timing not measured.**
6. **Cross-host reproducibility is unverified.** Builds are byte-identical across build
   *directories* on this host with the pinned toolchain. Reproducibility across different host
   distributions has not been demonstrated and must not be claimed.
7. **Backtrace names are approximate.** Fat LTO plus `--gc-sections` merges and discards many
   function symbols, so some frames resolve to the nearest preceding symbol rather than their
   own. `tools/symbolize` reports this explicitly instead of presenting an approximation as
   exact.
8. **No physical hardware bring-up.** The reference platform is QEMU only; selecting a
   physical desktop reference board is M1 work.

## Scope note: this M0 is narrower than some M0 definitions

The founder-supplied research report estimates M0 at roughly five months for three to six
experienced engineers. This M0 was completed far faster because it is **smaller**, not because
it was done faster: no physical-hardware bring-up, no crash-dump or symbol-server
infrastructure, one virtual reference platform rather than a selected physical one, and a
framebuffer that is discovered but deliberately never drawn to.

Recorded so early velocity is not mistaken for a schedule. See
[EFFORT-AND-RISK.md](EFFORT-AND-RISK.md) and
[the integration record](../research/deep-research-integration.md).

## Post-publication validation

- Fresh clone from GitHub onto a different filesystem: `tools/bootstrap`, `tools/doctor`,
  `tools/build` and `tools/test` all succeed, and the kernel boots with identical serial
  output. Executable bits survived the NTFS-to-ext4 transition correctly.
- CI passed on the published `main` (1m23s), running the same suite under TCG.
