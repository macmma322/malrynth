# H0.5 Gap Audit

**Status:** LOCKED (this audit records a point-in-time finding)
**Date:** 2026-08-19
**Baseline audited:** `main` @ `7a421b4` (M0 complete, CI green, fresh-clone green)

This audit was performed **before** any H0.5 document was written, so it records what was
genuinely absent rather than what was convenient to claim.

## Method

Every platform foundation named in the H0.5 brief was checked against the repository as it
stood at `7a421b4`. A subsystem counts as **specified** only if a document answers the
success criterion: *where it belongs, what it depends on, what depends on it, whether it is
privileged, which security boundary owns it, build-or-reuse, which API layer, when it can be
implemented, and what must be decided first.*

A paragraph mentioning a subsystem does **not** make it specified. That distinction is the
entire purpose of this audit, and it is why several rows below read "insufficient" rather than
"present".

## Verdict summary

| Verdict | Count |
|---|---|
| Sufficient as-is | 3 |
| Present but insufficient (needs substantial expansion) | 9 |
| Absent | 37 |
| Conflicting | 2 |

**M0 and the repository-topology work were sound. The platform above the kernel was almost
entirely unspecified.** That is the honest finding, and it is the reason H0.5 exists.

## Conflicts found

**C1 — application map location.** At the audited baseline the file was
`docs/application-map.md` (docs root), referenced by `README.md`, ADR-0001, `M7.md` and
`EFFORT-AND-RISK.md`. The H0.5 brief asks for `docs/apps/APPLICATION-MAP.md`.
**Resolution applied:** moved with `git mv`, substantially expanded, and every inbound
reference updated. Leaving two application maps would have guaranteed they diverge.

**C2 — product composition location.** At the audited baseline the file was
`docs/architecture/PRODUCT-COMPOSITION.md`; the brief asks for `docs/products/`.
**Resolution applied:** moved with `git mv`, expanded with per-product definitions, and all
references updated. No stale copy remains.

## What the audit says about the previous pass

The previous pass did exactly what it was asked and did it well: M0 is real, tested, and
honest about its limits. But its scope was the kernel and the repository, and it treated the
platform above the kernel as roadmap text.

The risk that creates is specific and worth naming: **M1–M4 make decisions that silently
foreclose platform options.** A virtualization primitive placed in the wrong layer, a memory
model that assumes one global address space, or an M2 syscall surface that hands out ambient
authority "temporarily" are all cheap now and very expensive at M5–M7. ADR-0004 began
addressing exactly this for the object model; H0.5 extends that discipline to the rest of the
platform.

## Scope discipline for H0.5

Per the brief, H0.5 produces **specifications only**. The sole permitted code changes are
those needed to keep M0 green, plus documentation and validation tooling.

One such fix was required and is recorded separately: the committed `.cargo/config.toml`
asserted that the non-PIE kernel invariant was enforced by `core/kernel/build.rs`, but the
link argument had never been committed — a bare `cargo build` produced `ET_DYN`. The loader's
`e_type` check made this loud rather than silent, which is why CI stayed green. Fixed in
`ed5621b`.
